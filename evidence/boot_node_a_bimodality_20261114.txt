--- [3] Cause Analysis & Working Hypotheses ---

Observed Facts:
1. Kernel boot is invariantly fast across all runs: 327 ms to 474 ms.
2. Port 22 (sshd) opens between 5.8 s and 8.5 s.
3. The slow ~16 s runs (Set 2 runs 8, 9, 10) have NO recorded guest telemetry; their exact internal breakdown is unknown.

Hypothesis (supported by telemetry in 1 of 5 fresh runs - Run 15):
- In Run 15, `pollinate.service` stalled for 6.517 s attempting an outbound network handshake to entropy.ubuntu.com across the host bridge NAT. This single service stall pushed total userspace boot from ~5.5 s to 10.96 s and overall SSH readiness to 13.958 s.
- It is hypothesized that intermittent outbound DNS/NAT packet drops or rate-limiting on restrictive networks (such as hostel Wi-Fi) cause network-dependent in-guest services (such as pollinate or cloud-init network checks) to block until timing out, contributing to observed jumps toward 14 s – 16 s.
- Other possible contributing factors during slow runs:
  * Host resource contention: during Set 2, the nested Node B outer VMM (4 vCPUs, 4GB RAM) was actively running alongside Node A.
  * SSH polling behavior: `-o ConnectTimeout=1` with 0.3s sleep adds ~1.3s per failed loop while sshd initializes host keys or processes login authentication.
  * Whether page cache drops, disk I/O flushes, or DHCP lease delays occurred during the Set 2 16 s runs cannot be proven definitively because in-guest telemetry was not captured for those specific runs.
